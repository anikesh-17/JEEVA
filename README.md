### Deep Dive into the Blockchain Mechanics
The ledger is built inside the backend utilizing Node's built-in `crypto` library.
* **Algorithm:** **SHA-256** (Secure Hash Algorithm 256-bit).
* **Hash Calculation:** The hash is a cryptographic signature generated by hashing:
  $$\text{Hash} = \text{SHA256}(\text{JSON.stringify}(recordData) + previousHash + timestamp + nonce)$$
* **Proof of Work (PoW):** Employs a difficulty factor of `2`. When mining a block, the engine loops, incrementing `nonce` until the resulting hash starts with `00`.
* **Storage:** Mined blocks are saved to a dedicated `blocks` collection in MongoDB, ensuring that history persists across restarts.

## 🏗️ How We Created It (Engineering History)

The engineering journey of JEEVA progressed through five iterative architectural stages:

### Phase 1: Frontend Client Scaffolding
We initialized a React project powered by Vite for fast hot-module replacement. Standard styling was replaced with **TailwindCSS** to build a charcoal-and-emerald themed user interface. We configured `react-router-dom` to manage Single Page Application routing across the Dashboard, Profile, AI Screenings, and Blockchain Audit Ledger.

### Phase 2: Python ML Engine Serialization
We built a decoupled Python Flask microservice to load pre-trained binary classifiers. Using `joblib`, we serialized trained scikit-learn models (such as random forests and SVMs). Flask endpoints were exposed to ingest patient vital vectors, compute diagnostic predictions, and output confidence values using `predict_proba()`.

### Phase 3: Blockchain Utility Architecture
To enforce immutability, we designed a custom blockchain registry inside Node.js. We defined a block structure consisting of an index, timestamp, medical record details (glucose, max heart rate, etc.), miner nonce, previous block hash, and current block hash. The Proof-of-Work hashing loop was tuned to process blocks instantly on local CPUs.

### Phase 4: Express Gateway & Database Connection
We set up an Express API backend and connected it to MongoDB via Mongoose. We created dual schemas: `User` (vitals, schedules, predictions) and `Block` (blockchain ledger data). To secure the API, we configured **Firebase Admin SDK** as a middleware wrapper, which inspects client request headers, decodes JWT tokens, and maps endpoints to authenticated Firebase users.

### 🔧 Key Integration Bugs & Resolutions
During assembly, we encountered and resolved several critical system bugs:

#### 1. Firebase Client Authentication Delay (Race Condition)
* **Problem:** React components initialized and attempted API database requests immediately upon mount. Since Firebase takes a short period to verify the user session on load, `auth.currentUser` initially returned `null`, throwing authentication errors and locking the screen.
* **Resolution:** We created an auth guard that checks for loading states (`!authLoading && user`) before issuing database fetches, keeping the UI loading spinner active until Firebase reports a verified session.

#### 2. Mongoose Array Subdocument ID Casting Crash (`BSONError`)
* **Problem:** Adding or removing appointments sent custom alphanumeric string IDs (e.g., `"vxz78p2aj"`) generated by the frontend. Mongoose automatically mapped the `id` key to `_id` and attempted to cast it to a standard 12-byte MongoDB ObjectId. This caused a casting error, crashing the backend.
* **Resolution:** In [User.js](file:///c:/Users/raghu/Downloads/JEEVA-main/JEEVA-main/backend/models/User.js), we updated the `AppointmentSchema` structure to explicitly set `_id: false` and registered `id: String`. This forces Mongoose to leave the frontend ID as a plain string, resolving scheduling operations.

#### 3. MSYS2 Python Package Compilation Blockers
* **Problem:** Installing standard scientific packages (SciPy, NumPy) via pip on Windows MSYS2 UCRT64 systems failed due to build compilation errors (requiring CMake, Ninja, and throwing SSL errors).
* **Resolution:** We bypassed PyPI source compilation by using MSYS2's native package manager (`pacman -S mingw-w64-ucrt-x86_64-python-numpy ...`) to download precompiled binaries, allowing Python's native scikit-learn dependencies to run instantly.

#### 4. Vite Dynamic Port Shifting and CORS Origin Errors
* **Problem:** If port `5173` was busy, Vite would run the frontend on `5174`. The backend rejected requests from `5174` since it wasn't listed in CORS origins.
* **Resolution:** We updated [server.js](file:///c:/Users/raghu/Downloads/JEEVA-main/JEEVA-main/backend/server.js) to whitelist both ports and configured Vite with strict port options (`--port 5173 --strictPort`) to prevent unexpected port shifting.

## 🙋 Expected Interviewer Q&A

#### 💬 Q1: Why use a custom private blockchain inside Node.js instead of a public network like Ethereum?
> *"Public blockchains store transaction data publicly and charge gas fees. For clinical applications, storing raw medical records on a public ledger violates privacy regulations like HIPAA, and gas fees make real-time predictions expensive. By using a private Proof-of-Work blockchain, we achieve zero transaction fees, high throughput, and data privacy, while maintaining cryptographic immutability."*

#### 💬 Q2: How does the decoupled Flask microservice benefit the application's lifecycle?
> *"Decoupling the ML service from the API gateway allows us to update and deploy prediction models independently. We can retrain models in Jupyter Notebooks, export them as pickle files, and deploy them to the Flask service without modifying the backend Node.js APIs or causing application downtime."*

#### 💬 Q3: How do you verify the integrity of the blockchain database records?
> *"The backend uses the `verifyChain()` function, which retrieves all blocks ordered by index. It reconstructs each block, recalculates its SHA-256 hash using the block's `nonce`, and asserts that it matches the stored `hash`. It then checks if the block's `previousHash` matches the hash of the preceding block. If any database document is edited, this cryptographic chain breaks."*
